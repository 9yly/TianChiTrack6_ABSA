# 电商评论观点挖掘方案分享

起于对业务价值的洞察：在电商场景里，评论已经成为消费者判断是否下单的关键，平台和品牌方都希望把评论里的“属性、观点、情感”要素及时抽取出来，用于舆情监控、产品改版和投放策略。官方训练数据虽然提供了标注四元组，却充满错别字、重复表述和大量隐式属性，传统基线模型很难在这种混合噪声中保持稳定，我们的首要目标是确保在测试集上按 ID 升序输出完整四元组，并尽可能提升 F1。带着这样的动机，我们评估了既有 Baseline 与实际需求之间的差距，最终决定围绕“模型微调 + RAG 检索增强”构建整个方案。

承接这个思路，我们先在自有机器上对 Qwen/Qwen2.5-32B-Instruct 做 LoRA 微调，训练数据按照竞赛格式组织成 JSON prompt，将 (AspectTerm, OpinionTerm, Category, Polarity) 的组合直接喂给模型。为了让模型正确处理隐式属性，我们在输入中混入了大量以 "_" 表示 aspect 的样本，并设计分阶段 prompt：第一阶段允许模型自由描述，第二阶段逐步收紧输出模板，直到模型稳定地只输出合法 JSON。训练里加入了梯度裁剪和少量 warmup 步骤，同时抽取 5% 的验证集做逐批次人工检查，重点看错位字段、冗余解释和非法类别。经过几轮超参调优后，微调模型在验证集上已经能把占位符和细粒度情感区分开，为后续推理搭好了基座。

然而仅靠微调依旧难以覆盖长尾表达，例如“客服态度太温柔我舍不得差评”这类隐含情绪语句容易被误判，于是我们转向构建检索增强模块。BM25 被用作第一阶段的粗召回，我们对 Train_reviews 进行分词建索引，查询时保留前 20 条候选，目标是尽量把相关样本召回来；虽然噪声较多，但能保证 Recall 不塌。第二阶段用 Ollama 在本地部署的 `BAAI/bge-reranker-v2-m3` 模型做精排，它对语义的捕捉比纯 BM25 更敏感，把“包装太随便了”和“盒子裂开了”这样的语义匹配关联起来，最终选出最贴近的 5 条样本。我们把这些样本转写成“评论文本 + 四元组”的 few-shot 提示放到 prompt 中，核心是给模型展示真实标注的结构化例子，让它在回答时不偏离官方模板。为了防止检索失败的样本影响整体推理，还对 Rerank 返回值做了容错处理，当候选不足时自动回退到 BM25 原结果。

落地阶段，我们精心调度 API 调用：ThreadPoolExecutor 控制并发度在 5 以内，保证稳定又兼顾速度，失败会按指数退避重试并记录到日志。每条预测会即时写入 JSONL，便于断点续跑和抽样审查。如果模型回传的 JSON 被污染，我们会尝试抽取首个合法大括号块，再用 Pydantic 校验每个字段是否合法类别、极性是否在 {正面, 中性, 负面} 中，否则自动剔除重复和违规条目。最终结果通过脚本统一升序排列写入 CSV，确保符合官方格式要求。

合乎预期的结果显示，这套方案在复现旧基线 F1 的基础上，针对复杂长句和隐式属性的召回率显著抬升，尤其是在多情感句子中能稳定输出多条四元组。我们总结出的经验包括：LoRA 微调为模型注入了遵循模板的能力；RAG 模块提供了语义邻近的“参考答案”，帮助模型在离散场景保持一致性；而并发执行和日志落盘则保证了大规模推理的工程稳定性。后续还计划探索更细粒度的实体检索，比如根据 AspectTerm 触发二次补救推理，或者引入轻量级对齐器来自动修正边界位置，为业务部署提供更高的鲁棒性。
